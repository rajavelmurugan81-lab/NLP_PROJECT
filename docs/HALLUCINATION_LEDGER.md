# CiteGuard Hallucination Ledger & Failure Signature Engine Documentation

## 1. Purpose

The **Hallucination Ledger** and **Failure Signature Engine** form Phase 5 of the CiteGuard framework. This component provides a structured, empirical, and reproducible system for recording, categorizing, and analyzing failure and hallucination patterns produced by scientific claim-verification pipelines.

Unlike generic evaluation systems that label every incorrect prediction simply as a "hallucination", CiteGuard strictly distinguishes failure types based on observable evidence, retrieval behavior, and reasoning output.

---

## 2. Terminology

- **Claim**: A scientific statement evaluated by the system.
- **Evidence**: Documents or passages retrieved to substantiate or refute a claim.
- **Ground Truth**: Human-annotated label (`SUPPORT`, `CONTRADICT`, `NEI`) and ground-truth document IDs.
- **System Prediction**: Label generated by the claim verification system.
- **Failure Signature**: Structured record detailing an incorrect or insufficient prediction attempt.
- **Hallucination**: A specific failure mode where generated claims/reasoning lack factual support or contradict retrieved evidence.
- **Hallucination Ledger**: Persistent, append-only, deduplicated storage for failure signatures across evaluation runs.

---

## 3. Failure Taxonomy

CiteGuard defines a controlled 10-category failure taxonomy (`FailureType`):

| Failure Category | Code | Description | Diagnostic Criteria |
| :--- | :--- | :--- | :--- |
| **No Evidence** | `NO_EVIDENCE` | No relevant evidence retrieved. | Top-K similarity / relevance score below threshold $\tau_{\text{retrieval}}$. |
| **Wrong Evidence** | `WRONG_EVIDENCE` | Retrieved evidence does not relate to the claim. | Top-K documents retrieved, but text similarity / ground-truth overlap is minimal. |
| **Insufficient Evidence** | `INSUFFICIENT_EVIDENCE` | Evidence is partially relevant but inconclusive. | Retrieved evidence lacks required granularity to confirm or refute claim. |
| **Contradictory Evidence** | `CONTRADICTORY_EVIDENCE` | Evidence conflicts with predicted conclusion. | System predicts `SUPPORT` while retrieved evidence refutes (or vice-versa). |
| **Partial Evidence** | `PARTIAL_EVIDENCE` | Evidence supports only a sub-part of claim. | Claim contains multiple propositions, but evidence covers a subset. |
| **Retrieval Failure** | `RETRIEVAL_FAILURE` | Ground-truth evidence exists but missing from top-K. | Ground-truth doc IDs known, but none appear in retrieved set. |
| **Reasoning Failure** | `REASONING_FAILURE` | Ground-truth evidence retrieved, but prediction wrong. | Ground-truth evidence present in top-K, but system misclassifies label. |
| **Label Failure** | `LABEL_FAILURE` | Classification error despite adequate evidence/reasoning. | Borderline or noisy label assignment where reasoning trace is valid. |
| **Source Quality Failure** | `SOURCE_QUALITY_FAILURE` | Retrieved source is unverified, low quality, or noisy. | Document metadata indicates low reliability or missing abstract text. |
| **Unknown Failure** | `UNKNOWN_FAILURE` | Failure cannot be confidently assigned to a category. | Fallback when observable evidence is ambiguous (prevents hallucinating causes). |

## 4. Failure Signature Schema

Each failure case is captured as a `FailureSignature` object:

```python
@dataclass
class FailureSignature:
    claim_id: str
    claim_text: str
    dataset: str
    split: str
    predicted_label: str
    ground_truth_label: str
    retrieved_document_ids: List[str]
    retrieved_ranks: List[int]
    retrieval_mode: str
    evidence_available: bool
    evidence_retrieved: bool
    failure_type: FailureType
    failure_subtype: Optional[str] = None
    confidence: Optional[float] = None
    explanation: Optional[str] = None
    timestamp: str = ""
    run_id: str = ""
    metadata: Dict[str, Any] = field(default_factory=dict)
    signature_hash: str = ""
```

### De-duplication Mechanism
Signatures compute a SHA256 `signature_hash` over `(run_id, dataset, claim_id, retrieval_mode, failure_type)`. The `HallucinationLedger` checks this hash before insertion to avoid duplicating records when evaluation scripts are executed repeatedly.

## 5. Classification Rules & Decision Logic

The `FailureAnalyzer` processes evaluation outputs according to deterministic precedence rules:

```

                  │ System Prediction == Ground  │
                  │            Truth?            │
                  └──────────────┬───────────────┘
                                 │
                   ┌─────────────┴─────────────┐
                   │                           │
                 [YES]                        [NO]
                   │                           │
         Return None (Correct)                 │
                                               ▼
                                 ┌───────────────────────────┐
                                 │ Ground-Truth Doc IDs      │
                                 │ Available & Non-Empty?    │
                                 └─────────────┬─────────────┘
                                               │
                                 ┌─────────────┴─────────────┐
                                 │                           │
                               [YES]                        [NO]
                                 │                           │

                   │ Is Ground-Truth Doc in    │             │

                                 │                           │
                  ┌──────────────┴──────────────┐            │

```

## 6. Retrieval vs. Reasoning Failure Distinction

A critical contribution of CiteGuard Phase 5 is the strict separation between:

1. **Retrieval Failure**: The information retrieval subsystem failed to surface ground-truth evidence into top-K results. Fix requires improving indexing, BM25 parameters, vector embeddings, or RRF fusion weights.
2. **Reasoning / Classification Failure**: The retrieval subsystem succeeded (ground-truth evidence is in top-K), but downstream decision logic misconstrued the relationship between claim and evidence. Fix requires model fine-tuning, prompt optimization, or multi-agent debate (Phase 6).

## 7. Storage Format & Querying

- **Primary Storage**: JSON Lines (`results/hallucination_ledger/hallucination_ledger.jsonl`).
- **Export Format**: CSV (`results/hallucination_ledger/hallucination_ledger_export.csv`).
- **Ledger Operations**:
  - `ledger.add_signature(signature)`: Add record (with duplicate prevention).
  - `ledger.query(...)`: Filter signatures by dataset, failure_type, retrieval_mode, run_id, label, etc.
  - `ledger.export_csv(path)`: Export filtered or all signatures to CSV.
  - `ledger.get_aggregate_statistics()`: Summarize total counts, rates, and distributions.

## 8. Failure Statistics & Visualizations

The `src/evaluation/failure_statistics.py` module calculates comprehensive metrics:
- Overall failure rates and percentages
- Failure counts broken down by `FailureType`
- Dataset-wise failure rates (`SciFact`, `CoVERT`, `SciClaimHunt`)
- Retrieval mode comparisons (`BM25` vs. `Dense` vs. `Hybrid`)
- Ground-truth and predicted label distributions

Visualization tables are automatically generated as CSV files under `results/hallucination_ledger/`:
- `failure_type_distribution.csv`
- `dataset_failure_distribution.csv`
- `retrieval_mode_comparison.csv`
- `label_failure_distribution.csv`

---

## 9. Limitations

1. **Ground-Truth Dependence**: Full separation between `RETRIEVAL_FAILURE` and `REASONING_FAILURE` requires annotated ground-truth document IDs. When ground-truth document IDs are absent, the system defaults to conservative categories or `UNKNOWN_FAILURE`.
2. **Deterministic Rules**: The analyzer currently relies on exact ID matching and boolean flags. LLM-based semantic reasoning evaluation will be added in future phases to detect nuanced sub-types like `PARTIAL_EVIDENCE` or `CONTRADICTORY_EVIDENCE`.
